# 改善点一覧

**作成日**: 2026年9月2日  
**対象**: `basic-next-js-app`

## 概要

現在のアプリケーションは、SQLiteからメッセージを取得して表示する最小構成として動作しています。ESLintと既存の39テストは成功しており、次の段階ではデータの正確性、テーマ切り替えの堅牢性、運用環境との整合性を優先して改善するのが効果的です。

## 優先度の高い改善

### 1. 最新メッセージの並び順を安定させる

`lib/database.ts` は `created_at DESC` のみで最新メッセージを取得しています。SQLiteの `CURRENT_TIMESTAMP` は秒精度のため、同じ秒に複数行が登録された場合、どの行が返るかが不定になります。

**対応案**

- `ORDER BY created_at DESC, id DESC` に変更する
- 作成日時の精度を上げる、またはIDをタイブレーカーとして利用する
- 同一時刻に複数件登録したケースのテストを追加する

### 3. SQLiteの運用環境を明確にする

`better-sqlite3` とローカルファイル `data/app.db` は開発や単一サーバーでは扱いやすい一方、Vercelなどのサーバーレス環境ではファイルの永続性やインスタンス間共有が保証されません。

**対応案**

- 開発用SQLiteと本番用データベースを分離する
- 本番ではVercel Postgres、Turso、Cloudflare D1などの永続ストレージを検討する
- SQLiteを継続利用する場合は、デプロイ先・書き込み可否・バックアップ方針をREADMEに明記する

## 優先度が中程度の改善

### 4. APIレスポンスの型とエラー形式を統一する

`src/app/page.tsx` はAPIレスポンスを暗黙に扱っているため、APIの形式が変わっても実行時まで検知できません。

**対応案**

- `{ message: string }` のレスポンス型を定義する
- 必要に応じてZodなどでレスポンスを検証する
- 成功・失敗レスポンスの形式を統一する
- クライアント側に「再試行」操作を追加する

### 5. クライアントフェッチの中断と状態管理を改善する

ページ遷移中に`fetch`が完了すると、不要なstate更新が発生する可能性があります。

**対応案**

- `AbortController` を使ってアンマウント時にリクエストを中断する
- `AbortError` は通常のエラー表示と区別する
- データ取得をServer Componentへ移す案も比較し、ローディングUIが必要な場合のみClient Componentを維持する

### 6. セキュリティヘッダーを設定する

`next.config.ts` は現在空の設定です。公開運用する場合は、ブラウザの基本的な防御設定を追加すると安全性を高められます。

**対応案**

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy`
- `Permissions-Policy`
- クリックジャッキング対策としての`frame-ancestors`または`X-Frame-Options`

Content Security Policyは、Next.jsの動作とインラインリソースへの影響を確認したうえで段階的に導入します。

## 開発体験・品質の改善

### 7. ドキュメントと設定の不一致を解消する

`README.md` に記載されたNext.js・Reactのバージョンが、現在の`package.json`と一致していません。また、READMEではCIがプルリクエストでも実行されると説明していますが、現行workflowのトリガーは`push`のみです。

**対応案**

- READMEの技術スタックと前提Node.jsバージョンを実際の設定に合わせる
- CIに`pull_request`トリガーを追加するか、READMEの説明を修正する
- バージョン情報を手作業で重複管理しない方法を検討する

### 8. テスト対象を実際の利用経路まで広げる

現在はデータベースとテーマ関連コンポーネントが中心です。APIとトップページの取得状態は未検証です。

**対応案**

- `/api/message` の成功・500エラーのテストを追加する
- ローディング、成功、失敗の画面表示をテストする
- テーマ切り替え時の`document.documentElement`のクラスを検証する
- 必要性が出た段階でPlaywrightによるE2Eテストを追加する

## 実施順序

1. データ取得の並び順とテーマ状態の不整合を修正する
2. API・クライアントの型、キャンセル、エラー表示を整理する
3. 本番データベース方針とセキュリティヘッダーを決定する
4. README、CI、テストを実装内容に合わせて更新する

各変更は小さな単位で実施し、`npm run lint`、`npm test`、`npm run build`を通過させてから取り込む方針とします。

## 完了条件

- 同一秒に作成されたメッセージでも、IDの大きい最新行が取得される
- テーマ状態とDOMのテーマクラスが常に一致する
- API異常時にクライアントが予期せずクラッシュせず、利用者に再試行可能な状態を示す
- 本番環境でSQLiteファイルを利用するかどうかと、データ永続性の前提が文書化されている
- README、CI設定、package.jsonの説明が一致している
